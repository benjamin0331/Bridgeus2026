## 一、必須做

### 1.1 確認「完成」的定義

我把「完成一場對話」實作成 **`PostDialogueResponse` 有一筆紀錄**（＝送出後測）。理由是這與成就頁的「完成前測與後測」「完成完整聊天流程」同義，而且它是唯一每場對話都留下一筆的耐久紀錄。H-H 與 H-AI 都算，不看 `experiment_condition`。

**如果你們認為「完成」該用別的判準**（例如 `DialogueMatch.status='closed'`、或要求輪數達標），改 `dialogue_level()` 的資料來源即可，門檻表不用動。

### 1.2 門檻表（已定案，不用再確認）

| 等級 | 顏色 | 門檻 | 級距 | 場次範圍 |
|---|---|---|---|---|
| Lv0 | 白 | 0 | — | 0–1 |
| Lv1 | 紅 | 2 | +2 | 2–4 |
| Lv2 | 橙 | 5 | +3 | 5–9 |
| Lv3 | 黃 | 10 | +5 | 10–16 |
| Lv4 | 綠 | 17 | +7 | 17–26 |
| Lv5 | 藍 | 27 | +10 | 27–39 |
| Lv6 | 紫 | 40 | +13 | 40+ |

級距遞增，後段升級愈來愈慢。門檻要調只改 `LEVEL_THRESHOLDS` 那一個 tuple，**前端與 Godot 都不用動**——Godot 色表與成就頁那張等級卡的場次都是從 `/titles/me/` 回傳的 `level_thresholds` 讀的，沒有任何地方抄第二份。

⚠️ 需要注意的是**實驗期的可達性**：8 個月、每人預估 2–5 場的話，多數受試者會停在 Lv1–2，Lv5/Lv6（27／40 場）實務上只有實驗結束後長期公開運作才看得到。這是教授指定的曲線，不是 bug，但如果希望受試者在實驗期內就有升級感，門檻要往下壓。

### 1.3 主功能必須把 token 交給 Godot

Godot 是靠 `window.bridgeus_token` / `window.bridgeus_user_id` 拿到身份（`Backend.gd::acquire_token_from_host()`）。**沒交接的話會退回 `guest_login`，而 `GuestLoginView` 每次都建一個新 User，累積場次永遠是 0 → 所有人都是 Lv0 白青蛙。**

主功能在把 Godot 場景嵌進 `<iframe>` 前，必須先設好這兩個 `window` 變數。這是既有契約（`godot-backend-integration.md` §1），但等級功能上線後它從「影響議題持久化」升級成「等級直接壞掉」，所以特別提醒。

## 二、該做

### 2.1 成就頁的等級卡目前吃寫死的示意資料 — 請確認端點通了

成就頁最上面新增了一張卡（`frontend/src/pages/LevelSummaryCard.jsx`）：左邊一隻大青蛙（上緣露出卡片外做層次），右邊三塊數字 **Godot 等級** / **已完成對話** / **離下一級還差幾場**，外加一個 hover 說明的小問號。背景是真的 Godot 地圖。

它打的是 `GET /api/titles/me/`，用第零節那三個欄位，**不需要任何新的後端欄位或端點**。但目前實測抓不到資料，所以卡上會顯示一個紅色虛線標籤「示意資料 · 後端尚未串接」，數字是寫死的（Lv2 橙 / 7 場 / 離 Lv3 差 3 場）。

**你要做的事**：確認下面兩件，然後回報給我，我把示意資料拿掉。

1. **後端有跑起來、而且是含我改動的版本**。`views.py` 的 `TitleMeView` 要有 `level` / `dialogue_count` / `level_thresholds` 三個欄位。舊的 uvicorn process 沒重啟的話不會有。驗證：
   ```bash
   curl -H "Authorization: Bearer <access token>" http://localhost:8000/api/titles/me/
   ```
   回傳裡要看到那三個欄位。
2. **前端的 API base 指對**。前端用 `VITE_API_BASE_URL`（沒設就打同源），dev 時要能從 Vite（5173）打到 Django。沒設 proxy 的話 `/api/...` 會打到 5173 自己而 404。

判斷方式很直接：**卡上還有那個紅色虛線標籤就代表沒串上**，瀏覽器 console 也會有一行「等級資料讀取失敗」。

串好之後要刪的東西（我留了註解標記）：`LevelSummaryCard.jsx` 的 `PLACEHOLDER` 常數、`isPlaceholder` state 與那個標籤、以及 `AchievementPage.css` 的 `.level-summary-placeholder`。

> 註：原本這一節是「請後端加 `last_shown_level` 欄位」（給 Godot 的等級彈窗記已讀狀態）。彈窗已經拿掉、改成這張常駐的卡，**那個欄位需求連帶取消了**，不用做。

### 2.2 稀有款彩虹蛙沒有任何紀錄

**需求**：每次進入 Godot 有 **1/10 機率**刷到彩虹青蛙（Lv777），取代該場的等級色，並跳恭喜彈窗。刷不到就正常顯示等級色。不持久化——下次進場重擲。

**目前做法**：純 client 端擲骰（`player_00.gd::roll_appearance()`），後端完全不知道。

**要不要記？** 如果研究上想知道「稀有款有沒有影響玩家的參與意願／留存」，就需要落地一筆事件（user、時間、是否刷到）。如果只是純彩蛋，不用記。**這是你們的研究設計決定，不是技術問題。**

## 三、成就系統的缺口（今天盤點出來的，跟等級無關但同一批）

盤點 `frontend/src/pages/achievements.data.js` 的 17 個成就，逐項對照現有資料。**目前 `unlocked` 是前端靜態值，沒有任何解鎖狀態落地。**

### ✅ 資料已足夠，現在就能算

| 成就 | 資料來源 |
|---|---|
| 第一聲問候 / AI 初體驗 | `PostDialogueResponse.experiment_condition` = `hh` / `ai` |
| 一念之間 / 保持初心 / 換個角度 | `PostDialogueResponse.delta_s_value` |
| 思辨旅程 | `PostDialogueResponse` 中 `s_pre` 非 null 的筆數 |
| 話匣子（高輪數） | `MatchMessage` / `AIConversation` 的 `count()`，需定義門檻 |
| 留到最後 / 百戰交流 | `PostDialogueResponse` 筆數（＝等級用的同一個數） |
| 今晚聊個夠 | `PostDialogueResponse.created_at` 按日 group by |

**輪數沒有 counter 欄位，但算得出來**：H-H 用 `MatchMessage.objects.filter(match=m).count()`，H-AI 用 `AIConversation.objects.filter(session_id=s).count()`（每列＝一問一答）。`DialogueMatch.stats` 只存 presence 與 semantic_tree，不含輪數。

### ⚠️ 偵測有做，但結果沒存 — 最大缺口

「理性交流」「有話好說」這兩個成就需要「這場有沒有攻擊性內容」，但：

- `api/consumers.py:412` 確實跑了 `check_content_sync()`。
- `self.blocked_count`（`consumers.py:358`、`419`）是 **WebSocket 連線的記憶體變數，累加後從來沒有人讀它**，斷線就歸零。等於死變數。
- `self.system_prompts_triggered`（`consumers.py:763`）同樣只在記憶體。
- `_send_system_prompt()` 只把訊息 send 給前端，**不寫 DB**。
- `MatchAISuggestion` 有落地，但 `Category` 只有 `rephrase` / `direction` / `redirect`，**沒有 blocked** —— 那是改述建議的紀錄，不是攻擊性事件的紀錄。

另外兩個限制：偵測只在 `hh_ai_assist_enabled()` 開啟時才跑，而且**只有 H-H**；H-AI 那條路徑不過濾。

**建議**：`MatchMessage` 加一個 `is_blocked`（或存 filter 的完整判定結果），把 `blocked_count` 那個死變數換成 DB 寫入。順帶決定 H-AI 要不要也過濾。這同時也讓「未偵測到攻擊性」這件事在研究上可稽核。

### ❌ 完全沒有資料

| 成就 | 缺什麼 |
|---|---|
| 初來乍到 | 可用 `User.date_joined`，勉強算有 |
| 初入異次元（首次進入 Godot） | 沒有進入紀錄。`GodotMatchRoomView` 記的是配對建房，不是進場 |
| 求知若渴（首次開啟知識庫） | `KnowledgeBase*View` 是純讀取端點，沒有 per-user 存取紀錄 |
| 常回來看看（累積使用天數） | **沒有登入歷史表**。`User.last_login` 只有最後一次、會被覆蓋，算不出天數 |
| 一路同行（收藏全部成就） | 要先有解鎖狀態落地 |

**建議優先序**：
1. 攻擊性事件落地（解鎖 2 個成就 ＋ 研究資料可稽核）
2. 每日活躍紀錄（一張 `(user, date)` unique 的小表，登入或發言時 upsert）
3. `UserAchievement` 解鎖狀態表 —— `UserTitle` 已經存在且註解寫著「由主功能成就系統決定」，但那個系統還沒實作
