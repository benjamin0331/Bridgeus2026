## What this is

BridgeUs — a 2D social-RPG prototype in **Godot 4.7** (GL Compatibility renderer, d3d12 on Windows). Two players meet in a shared world, post a discussion 議題 (issue) above their head, walk up to each other, read each other's issue, and start a 1-on-1 chat. The whole flow runs on **Godot's own multiplayer** (`WebSocketMultiplayerPeer`, port 8085 — 8080 is taken by React/Docker on this same dev box); a Django backend integration is live behind a seam (see below).

## Running

No build/lint/test CLI — this is an editor-driven Godot project. Open it in the Godot 4.7 editor and press Play, or `godot --path .`. Main scene is `World/Game.tscn`.

To exercise multiplayer you need **two running instances**: one clicks **Host** (`create_server`), the other clicks **Join** (`create_client` to `127.0.0.1:8085`). In the editor: Debug → Run Multiple Instances → 2. There is no automated test harness despite the "multiplayer synchronization test" commit.

## Architecture — the load-bearing decisions

**All cross-peer RPCs live on the player node, never on the UI.** A player is named `str(peer_id)` and lives at `/root/Game/<peer_id>` — an *identical path on every peer*, which is what makes `rpc_id` targeting work. The UI (`UI/game_ui.gd`, registered in the `issue_ui` group) is a screen-space `CanvasLayer` that is **local-only and contains zero RPCs**; it calls into the local player for anything networked, and the player calls back into the UI (found via the `issue_ui` group) to display incoming events. Keep this split — moving an RPC onto the UI breaks path resolution across peers.

**Spawn flow (ticket-based identity, not client-declared):** `request_spawn(id)` is gone — the old version trusted whatever peer id the client sent, so a modified client could claim to be anyone. The replacement is `submit_ticket.rpc_id(1, ticket)`: the client's `_on_join_pressed` first (on Web only) awaits `Backend.request_entry_ticket()`, a coroutine that asks the **host page** (`GodotLobby.jsx`'s `window.bridgeus_request_ticket()`) for a one-time, 60s-TTL entry ticket and polls `window.bridgeus_ticket` for the result — pulled fresh before every connection attempt, not pushed at iframe load, because a pushed ticket wouldn't survive WASM cold-start or a reconnect. Once `connected_to_server` fires, the client sends that ticket via `submit_ticket`; the server never trusts a self-reported id — it always reads `get_remote_sender_id()`.

On the server, `submit_ticket` branches on `Backend.service_token`. **Local dev** (`service_token == ""`, i.e. a desktop host with no `GODOT_SERVICE_TOKEN` in the environment): no service key means no way to redeem tickets against the backend, so the server spawns the peer with no identity at all — pure local play. **Production** (dedicated server, service key present): the ticket is redeemed via `Backend.redeem_ticket()` (POST with `X-Godot-Service-Token`) into a real backend `user_id`; failure of any kind (invalid/expired/reused ticket, network error) is uniform — the caller just `disconnect_peer`s, no reason is distinguished because there's only one thing to do with it. On success the `user_id` is recorded in `game.gd`'s `_peer_users` — a `peer_id -> user_id` dict that is **server-only and never synced** (any client-writable synced property is a property a client can forge; see the seat-assignment note below). Only after this does `_spawn_player` run, `add_child`ing `player_00.tscn` named `str(id)` under `Game`; the `MultiplayerSpawner` (`spawn_path=".."` → `Game`) replicates it to everyone. Each player sets its own multiplayer authority from its name in `_enter_tree`; `is_multiplayer_authority()` gates input, camera, and proximity detection so only the local player is driven.

**Random appearance & animation:** all character looks live as animation pairs (`char_N_idle` / `char_N_run`) in the single player scene's one `AnimatedSprite2D` SpriteFrames — no per-character scene. At spawn the authority rolls `appearance = randi() % <count>` (count derived from the `char_N_idle` animations, so adding a character = add its two animations, no code change). `appearance` + a `moving` bool are synced via the MultiplayerSynchronizer (`spawn=true`, so late joiners get the right look); every peer's `_process` plays `char_{appearance}_{idle|run}` and `flip_h` (synced) handles left-facing. Sizing: `_update_anim` normalizes every character to `SPRITE_PX` tall via `scale = SPRITE_PX / frame_height`, applied **once per appearance** (tracked by `_scaled_for`, decoupled from idle/run switching — else the scale only landed on the first animation change and the sprite visibly resized when it started moving). With uniform-spec art (all frames the same px) this yields one scale for everyone.

**Issue broadcast & live refresh:** `submit_issue` → `apply_issue.rpc(...)` (`@rpc("authority","call_local","reliable")`) runs on every peer, sets `issue_title/_body`, updates the head bubble, and calls `ui.refresh_menu()` so a bystander already standing in proximity sees「（對方尚未提交議題）」flip to the real title without re-entering range. **Late joiners get issues too**: on connect, `game.gd` fires `request_issue_sync.rpc()`, and every authority re-sends its issue (and banner/reactions) to the requester via `apply_*.rpc_id`. This is the one late-join catch-up path — RPCs alone don't reach peers who join later.

**Issue reactions (表情回復):** while reading someone's issue, you pick **one** of 5 emoji (Read panel bottom-row buttons) — one reaction per reader per issue. The emojis live in `Globals/Emoji.gd` — a `class_name Emoji` static atlas table (16×16 grid) shared by buttons, head display, and the count column; `Emoji.tex(i)` / `Emoji.REGIONS`. Not an autoload (pure data). Flow mirrors issues: reader → `react_to_issue` → `add_reaction.rpc_id(author)` → **author holds one-per-reader, changeable** via `_reactor_ids` (a `{sender_id: idx}` dict keyed on `get_remote_sender_id()`, authority-only, not synced — reacting overwrites that sender's value; `reactions = _reactor_ids.values()` is derived from it, so a re-pick swaps the emoji in place without reordering the head row) → `apply_reactions.rpc(...)` broadcasts the whole idx list → every peer rebuilds the world-space head row (overlapping ~half via HBox `separation=-8`, no background, capped at `HEAD_MAX`=10 then「…」). Because the head is ambiguous at a glance, the Read panel's **right column** lists all 5 emoji with per-idx counts (`emoji ×N`), tallied from `_target.reactions` and refreshed live via `on_reactions_changed`. Reader-side, `_reacted_targets` tracks the reader's current pick per target; the chosen one shows a gray bottom bar and pressing another emoji re-picks (moves the bar, overwrites author-side). `apply_issue` clears both `reactions` and `_reactor_ids` (re-submit/delete wipes reactions) and calls `on_issue_reset` so readers' local locks clear too. Late joiners get reactions via `request_issue_sync`, sent **after** the issue (apply_issue clears, so order matters).

**Invite/chat handshake** is a chain of `@rpc("any_peer","reliable")` calls between the two players' nodes (`receive_invite` → `invite_result` → `send_chat`/`receive_chat` → `peer_left_chat`). Godot 4 `server_relay` (on by default) relays client↔client RPCs through the host, so host and client are symmetric.

**Voice call** (`Globals/VoiceChat.gd`, autoload) mirrors the chat handshake and is the project's second-largest subsystem, even though it's easy to miss reading only `game.gd`. `player_00.gd` has its own handshake chain — `invite_to_voice` → `receive_voice_invite` → `respond_voice_invite`/`voice_invite_result` → `leave_voice`/`peer_left_voice` — structurally identical to the chat invite chain above. Once accepted, `VoiceChat.start()` builds the DSP graph: microphone → a dynamically-created `VoiceMic` audio bus (there is no such bus in the scene tree beforehand; `AudioServer.add_bus` creates it at call time and `stop()` tears it down) → `AudioEffectPitchShift` (scale adjustable live from a UI slider, 0.5 deep voice ~ 2.0 chipmunk) → `AudioEffectCapture` (grabs post-effect frames for network transport) → `AudioEffectSpectrumAnalyzer` (feeds the UI's voice-activity bars). Capture and the analyzer are pinned at the end of the effect chain deliberately — both transport and visualization operate on the pitch-shifted audio, not the raw mic input. Every frame, the authority side pulls captured frames and ships them with `receive_voice.rpc_id(_voice_peer, frames)` — an unreliable RPC carrying a raw `PackedVector2Array` of PCM samples, played back on the receiving end through an `AudioStreamGenerator`.

## Conventions that bit us (don't relitigate)

- **Collision layers:** players are on **layer 2, mask 1** so they pass *through* each other but still collide with the environment (`Boundry`/walls must stay on layer 1, "Environment"). Without this, `move_and_slide` overlap-recovery shoves the other player. The proximity `Area2D` uses `collision_mask = 2` and group-filters to `players` in its callback.
- **Head bubble** lives in *world space* under the player, so the 2× camera zoom doubles it: font is rasterized at 18px and the box scaled `BUBBLE_SCALE = 0.5` to land crisp 1:1 on screen. `BUBBLE_Y` is the vertical offset above the player origin — a hand-tuned constant (the sprite *frame* is 144px tall but the visible creature's head sits near y≈−10), adjust it in the editor by eye.

## Backend seam

`Globals/Backend.gd` is the single seam to the Django backend — every network-facing call routes through it via native `HTTPRequest`. `guest_login` is **gone** (removed along with the client-declared-identity model it enabled — see Spawn flow above); no anonymous, unowned accounts get created anymore. `submit_issue` and `request_topic_match` are **live**; `analyze_stance/_emotion` return null (intentionally unimplemented, nullable placeholders reserved). The backend is optional — no server = local-only play (issues still broadcast, just not persisted). In this monorepo the Django backend lives in `../backend/` (runs on port 8005); the `issues`/`godot` endpoints `Backend.gd` calls are wired in `../backend/api/urls.py`. The integration spec, endpoint gap-analysis, and web-deployment plan are maintained by the team as separate design docs outside this repo (`godot/.gitignore` excludes `docs/`, so no versioned copy lives here).

`BASE_URL` is now a `var`, not `const`: desktop dev keeps `http://localhost:8005/api`; Web builds default to same-origin `/api` (the whole stack — frontend, API, Godot static files, Godot WS — sits behind one Cloudflare-tunneled domain, path-routed) unless the host page sets `window.bridgeus_api_base` first. `service_token` is a second, unrelated secret: read from the `GODOT_SERVICE_TOKEN` env var, **only ever populated on the headless dedicated server** (never in a Web export — `OS.has_feature("web")` is false there, and it's never set from `window.*`).

There are now **two separate identity channels**, and mixing them up is the easiest way to misread this codebase:
- `acquire_token_from_host()` reads `window.bridgeus_token` from the host page and sets `Backend.access_token` — a real login JWT the **client itself** uses to call `submit_issue`/`get_my_titles`/`set_my_title`/reaction endpoints directly. It only ever returns a token now, not a `user_id` — there is no `Backend.user_id` field; that field does not exist anymore.
- `request_entry_ticket()` (client-side coroutine, **must be awaited**) always suspends — it opens with an unconditional `await get_tree().process_frame` before branching into the Web polling loop or the desktop early-return, so desktop and Web both come back as a completion Signal, never a plain value. This is deliberate: two-instance desktop testing is this project's actual acceptance path, and if desktop returned synchronously while Web suspended, a missing `await` would compile, run fine in the desktop test everyone actually runs, and only fail — silently — once it shipped to Web. Making both paths suspend identically means the mistake fails the same way everywhere, including the desktop test. It asks the host page for a one-time entry ticket and hands it to the game server via `submit_ticket`, purely to prove which backend account is joining the multiplayer session. `redeem_ticket()` is the server-side counterpart (dedicated server only, requires `service_token`) that exchanges that ticket for a `user_id` by calling the backend.

`request_topic_match` POSTs to `/godot/match-rooms/` with an `X-Godot-Service-Token` header and the two players' **backend `user_id`s**, not Godot peer_ids — sourced from `game.gd`'s server-only `_peer_users` identity table (see `_do_seat`), never from anything synced on the player node. The backend endpoint now exists (`../backend/api/views.py` `GodotMatchRoomView`) and is idempotent: 201 creates a room, 200 means this pair already had an active room for this topic and it was reused, so a retry can't strand the two players in different rooms.

## Deployment (dedicated server)

A browser tab can't `create_server` — the Web export can only ever `create_client`. `game.gd::_is_dedicated_server()` detects the headless deployment target two ways (`--server` on the command line, matching the systemd `ExecStart` ops runs; or `DisplayServer.get_name() == "headless"` as a fallback that doesn't depend on any export preset) and short-circuits `_ready()` into `_start_dedicated_server()`: it opens the WebSocket server and returns *before* the UI wiring, banner setup, or `Backend` identity handshake run — a dedicated server represents no player and must never call `acquire_token_from_host`. A dedicated server that comes up **without** `GODOT_SERVICE_TOKEN` set refuses to start at all (`push_error` + `quit(1)`) rather than limping along unable to redeem tickets or build match rooms — a deploy with the env var missing should fail loudly at boot, not surface later as an inexplicable in-game rejection. On Web, `OS.has_feature("web")` hides the Host button (nothing left that could call `create_server` anyway) and leaves Join as the sole entry point. The connection address is resolved once in `_resolve_connection_settings()`: Web reads `window.bridgeus_ws_url` (falls back to the local desktop address if unset), desktop always uses the local default — replacing the old hardcoded `PORT`/`ADDRESS` constants (renamed `DEFAULT_PORT`/`DEFAULT_ADDRESS`, now only the fallback, not the only option).

**Local-dev seating looks like a bug but isn't:** a desktop host has no `GODOT_SERVICE_TOKEN`, so every peer that joins it spawns with no entry in `_peer_users` (see Spawn flow above). If two such peers sit on the two trunks of the same topic, `_do_seat` finds both `user_ids` are `0`, refuses to call `request_topic_match`, and **evicts both players from their seats** with `seat_denied("配對需要正式登入身份，請從主功能頁面進入")`. This is intentional — sending `[0, 0]` to the backend would either 400 silently or, worse, fabricate a match between two unrelated real accounts if the backend ever stopped validating — but it reads exactly like a two-player desktop test failing to pair up, and *will* get reported as a regression if a future contributor doesn't know why. The fix, for testing this path locally, is to run a real dedicated server with a valid service token, not to "fix" the eviction.

A ~25s any-peer heartbeat RPC (`_heartbeat`, unreliable, empty body) fires from `_process` whenever the multiplayer peer is connected, to keep Cloudflare's WebSocket idle timeout (~100s) from closing quiet connections. The interval is a fixed constant, not configurable — it only needs to comfortably undercut the platform's timeout, not track it precisely.

`_on_join_pressed`'s first `await` used to be a fixed `get_tree().create_timer(0.2).timeout` — guessing when the WebSocket handshake finished before firing the old `request_spawn`. That fixed wait is gone twice over: the connect step now awaits `Backend.request_entry_ticket()` (Web only, to get a ticket before even calling `create_client`), and the join itself waits on a one-shot `connected_to_server` signal before `submit_ticket.rpc_id(1, _ticket)` — real network latency (especially through a Cloudflare Tunnel hop) isn't guaranteed to fit in 200ms. The **second** 0.2s wait (after `submit_ticket`, before `request_issue_sync`, giving the `MultiplayerSpawner`'s initial replication a moment to land) is unchanged — it isn't a handshake wait and wasn't in scope for that fix.
